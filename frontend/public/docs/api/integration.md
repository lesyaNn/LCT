# Подключение и примеры

API позволяет работать с CRM из другого приложения. Это те же методы, которыми пользуется интерфейс: отдельной базы или обхода прав для интеграций нет.

Базовый путь: `/api/v1`. На вкладке Все методы находится контракт запущенного бэкенда. Там можно проверить параметры, обязательные поля, ответы и разрешённые роли. Кнопка Скачать OpenAPI сохраняет JSON для Postman или генератора клиента.

## Что можно делать

| Раздел | Операции |
|---|---|
| Вузы | Поиск, создание, просмотр паспорта, изменение и удаление |
| Справочники | Направления, программы, продукты, вендоры и ответственные |
| Договоры и лицензии | Создание, изменение, просмотр сроков, удаление; файлы договоров |
| Встречи | Создание, просмотр, изменение и удаление; повестка этапа 3 в JSON и PDF |
| Workflow | Шаблоны, запуск процесса, задачи, переходы, возврат этапа, комментарии и вложения |
| Отчёты | Предпросмотр, постановка в очередь, проверка статуса и скачивание результата |
| Аналитика | Сводка, матрица программ, Health Score |
| Импорт | Загрузка XLSX, проверка листа, запуск обработки и отчёт об ошибках |
| Внешние данные | Приём статистики LMS и заявок сайта |
| Пользователи | Приглашение, изменение, блокировка и запрос сброса пароля |
| Уведомления и аудит | Чтение уведомлений, отметка о прочтении, журнал действий |
| ИИ | Вопросы по документации и личная история диалогов |

Не у каждой сущности есть полный набор CRUD. Например, Workflow архивируется, а не удаляется целиком. Проверяйте конкретный метод, а не составляйте URL по аналогии.

Учёта тендеров в этой версии нет. Договоры и лицензии не являются тендерами. Пути `/tenders` нет.

## Авторизация пользователя

Пользователь входит через Keycloak. Каждый защищённый запрос содержит access token:

```http
GET /api/v1/auth/me HTTP/1.1
Authorization: Bearer <ACCESS_TOKEN>
Accept: application/json
```

Нужен access token, не ID token и не токен SourceCraft. Бэкенд проверяет подпись RS256, срок действия, issuer и audience. В типовой конфигурации audience равен `rtk-api`. Адрес Keycloak и audience текущего стенда возвращает `GET /api/v1/service-api`.

Для фронтенда используйте существующий `apiFetch` из `shared/lib/api-client.ts`. Он добавляет токен и обрабатывает обновление сессии. Не храните токен в localStorage и не вставляйте его в URL.

## Подключение серверного сервиса

Для обмена без пользователя администратор Keycloak создаёт отдельный OIDC client. Не включайте этот режим у публичного клиента фронтенда.

1. Включите Client authentication и Service accounts roles. Отключите ненужные способы входа.
2. Назначьте сервисному аккаунту минимально необходимую realm role: `user` или `manager`. Создание вуза требует `admin`; это не повод выдавать `admin` любой интеграции.
3. Настройте audience mapper так, чтобы access token содержал `rtk-api`, либо значение `KEYCLOAK_AUDIENCE` вашего стенда.
4. Для ограниченного доступа настройте claim `university_ids` как массив UUID доступных вузов. Пустой или отсутствующий список не даёт обычной роли доступ ко всем вузам.
5. Передайте client secret только серверу интеграции. Не добавляйте его в frontend или репозиторий.

Сервис получает access token у Keycloak с `grant_type=client_credentials`. По умолчанию такой клиент в репозитории не создаётся: его настраивает администратор стенда. Схема обмена описана в [документации Keycloak](https://www.keycloak.org/docs/latest/server_admin/#_service_accounts).

```http
POST /realms/rtk/protocol/openid-connect/token HTTP/1.1
Host: <KEYCLOAK_HOST>
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=<CLIENT_ID>&client_secret=<URL_ENCODED_SECRET>
```

Используйте `access_token` из ответа как Bearer. Перед истечением `expires_in` получите новый токен. Не рассчитывайте на refresh token для этого режима. В рабочей среде запросы к CRM и Keycloak должны идти по HTTPS.

## Права и область доступа

Роль проверяется отдельно от доступа к объекту. Наличие нужной роли не означает доступ к каждому вузу или чужому диалогу ИИ.

| Роль | Обычные возможности |
|---|---|
| `user` | Чтение доступных данных, работа с этапами и задачами, отчёты, ИИ |
| `manager` | Чтение доступных данных, работа с процессами, назначение пользователей и ответственных в своей области, аудит |
| `admin` | Создание, изменение и удаление записей каталогов, импорт, управление пользователями и шаблонами |

Это обзор, не замена матрицы конкретного метода. Создание, изменение названия или города и удаление вуза требуют `catalog.manage`, которое есть у `admin`. Руководитель не администрирует каталоги и импорт, но может менять разрешённые связи в паспорте и назначения в своей области. В каталоге API отображаются фактические проверки каждого маршрута.

`role_allowed` в каталоге показывает только проверку роли и прав. Ограничения по вузу, авторству, текущему этапу и связям проверяются при выполнении операции. Чужие объекты могут возвращать 404, даже если они существуют.

## Список вузов

Примеры curl рассчитаны на Bash. Замените `https://crm.example` адресом стенда. В PowerShell используйте `curl.exe` и подходящее для вашей оболочки экранирование.

```bash
curl 'https://crm.example/api/v1/universities?page=1&page_size=20&search=Москва' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>'
```

У списка есть `items`, `total`, `page`, `page_size`. `page` начинается с 1. Для вузов `page_size` по умолчанию 20, максимум 100. У истории ИИ максимум 50; ограничения разных методов могут отличаться.

Параметры `search`, `city`, `sort_by`, `sort_order` и фильтры показаны в карточке метода. Значения нужно URL-кодировать. При передаче массива UUID используйте формат из OpenAPI, обычно повтор параметра: `university_ids=<UUID_1>&university_ids=<UUID_2>`.

## Создание вуза

Нужна роль `admin`.

```bash
curl --request POST 'https://crm.example/api/v1/universities' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data-raw '{"name":"Тестовый университет","city":"Москва"}'
```

Ответ HTTP 201:

```json
{
  "id": "11111111-1111-4111-8111-111111111111",
  "name": "Тестовый университет",
  "city": "Москва",
  "created_at": "2026-10-17T10:00:00Z",
  "updated_at": "2026-10-17T10:00:00Z",
  "responsibles": []
}
```

ID и время в примерах условные. В следующих запросах используйте ID из настоящего ответа. UUID связанных записей должен существовать в CRM; случайный UUID не создаёт связь.

## Изменение вуза

Нужна роль `admin` с правом `catalog.manage`.

```bash
curl --request PATCH 'https://crm.example/api/v1/universities/<UNIVERSITY_ID>' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --header 'Content-Type: application/json' \
  --data-raw '{"city":"Казань"}'
```

Ответ HTTP 200 содержит обновлённую карточку вуза. PATCH меняет только переданные поля. Пропущенное поле и `null` не равнозначны; возможность очистки смотрите в схеме нужного поля. В данном примере название не меняется.

## Удаление вуза

Нужна роль `admin` с правом `catalog.manage`.

```bash
curl --request DELETE 'https://crm.example/api/v1/universities/<UNIVERSITY_ID>' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>'
```

При успехе возвращается HTTP 204 без тела. Не разбирайте его как JSON. Удаление безвозвратное. Если у вуза есть связанные записи, сервер вернёт 409; каскадного удаления всего паспорта этот метод не делает. Не запускайте удаление зависимостей автоматически.

Для проверки интеграции создайте отдельный тестовый вуз. Не проверяйте DELETE на рабочих данных.

## Программа и привязка к вузу

Сначала создайте программу каталога через `POST /api/v1/programs`. В `direction_id` передайте ID существующего направления:

```json
{
  "direction_id": "44444444-4444-4444-8444-444444444444",
  "name": "Анализ данных",
  "description": "Базовый курс"
}
```

Затем передайте её ID в `POST /api/v1/universities/{university_id}/programs`:

```json
{
  "program_id": "22222222-2222-4222-8222-222222222222",
  "status": "planned"
}
```

Создание программы в каталоге не привязывает её ко всем вузам. Продукты и ответственные тоже связываются отдельными методами.

## Договор и лицензия

Пример тела `POST /api/v1/contracts`:

```json
{
  "university_id": "11111111-1111-4111-8111-111111111111",
  "contract_number": "DEMO-001",
  "signed_at": "2026-10-17",
  "expires_at": "2027-10-17",
  "status_raw": "signed"
}
```

Пример тела `POST /api/v1/licenses`:

```json
{
  "university_id": "11111111-1111-4111-8111-111111111111",
  "product_id": "33333333-3333-4333-8333-333333333333",
  "license_number": "DEMO-LIC-001",
  "signed_at": "2026-10-17",
  "expires_at": "2027-10-17"
}
```

Оба метода возвращают HTTP 201 с созданной записью. Для изменения есть PATCH, для удаления DELETE. `status` и `days_to_expiry` рассчитывает сервер: передавать их вместо исходных полей не нужно. Чтобы прикрепить файл договора, используйте `/contracts/{contract_id}/file` с `multipart/form-data`.

Паспорт лицензии формируется через `GET /api/v1/universities/{university_id}/licenses/{license_id}/passport.pdf` с авторизацией и доступом к вузу. Проверка по QR ведёт на публичный `GET /api/v1/public/licenses/{license_id}/verification`: этому запросу токен не нужен. В каталоге он отмечен как публичный, `authentication_required` равен `false`. Это отдельное исключение, оно не открывает без входа создание, изменение, удаление или скачивание паспорта лицензии.

## Встреча

Тело `POST /api/v1/universities/{university_id}/meetings`:

```json
{
  "subject": "Обсуждение учебной программы",
  "meeting_type": "online",
  "meeting_at": "2026-10-20T10:00:00+03:00",
  "participants": []
}
```

Время встречи должно содержать часовой пояс. Для повестки этапа 3 есть отдельные GET `/workflow/instances/{instance_id}/meeting-agenda` и `/workflow/instances/{instance_id}/meeting-agenda.pdf`. Второй метод возвращает PDF, не JSON.

## Workflow

Тело `POST /api/v1/workflow/instances`:

```json
{
  "university_id": "11111111-1111-4111-8111-111111111111",
  "template_id": "55555555-5555-4555-8555-555555555555",
  "program_id": "22222222-2222-4222-8222-222222222222"
}
```

Для перехода сначала получите разрешённые цели через `GET /workflow/instances/{instance_id}/allowed-transitions`. Для возврата есть `/rollback-targets` и `/rollback`. Не меняйте этап обычным PATCH и не подставляйте ID этапа шаблона вместо ID этапа экземпляра.

## Отчёт

Отправьте `POST /api/v1/reports`:

```json
{
  "format": "xlsx",
  "filters": {}
}
```

Ответ HTTP 202:

```json
{
  "job_id": "66666666-6666-4666-8666-666666666666",
  "status": "queued"
}
```

1. Проверяйте `GET /api/v1/reports/{job_id}` с паузой, например две секунды.
2. Пока статус `queued` или `building`, продолжайте ждать.
3. При `ready` скачайте `GET /api/v1/reports/{job_id}/download`.
4. При `failed` покажите `error_message` и остановите опрос.

Постановка в очередь не означает готовность файла. Нужен запущенный worker отчётов. Срок скачивания возвращается в `expires_at`. Для выбора формата и колонок смотрите схему ReportRequest. При скачивании используйте бинарный ответ и `Content-Disposition`, не вызывайте `response.json()`.

## Загрузка файла

Пример первого шага импорта:

```bash
curl --request POST 'https://crm.example/api/v1/import/upload' \
  --header 'Authorization: Bearer <ACCESS_TOKEN>' \
  --form 'file=@catalog.xlsx'
```

Не устанавливайте Content-Type вручную: curl или браузер добавит multipart boundary. После загрузки проверьте лист через `/import/sheets/preview`, затем вызывайте `/import/execute`. Точные поля и ID смотрите в ответе загрузки и схеме каждого шага.

## Статистика LMS

Тело `POST /api/v1/integrations/lms/ingest`:

```json
{
  "university_id": "11111111-1111-4111-8111-111111111111",
  "programs": [
    {
      "program_id": "22222222-2222-4222-8222-222222222222",
      "learners_count": 24,
      "flows_count": 2
    }
  ]
}
```

Метод принимает агрегированные счётчики, не список персональных данных учащихся. Программа должна быть связана с указанным вузом. Для заявок сайта есть `/integrations/website/ingest`. Демо-синхронизация `/integrations/sync` не является готовым адаптером к реальной внешней LMS; её доступность проверяется через `/integrations/capabilities`.

## ИИ-помощник

Тело `POST /api/v1/assistant/chat`:

```json
{
  "message": "Как скачать отчёт?",
  "page": "reports"
}
```

Помощник отвечает по документации и не создаёт объекты CRM. Он возвращает обычный JSON, не поток. Для продолжения передайте `conversation_id` и последнюю `expected_revision`. В ответе есть `answer`, `basis`, `sources` и `revision`. `model: null` допустим для готового ответа из FAQ. Статус готовности проверяется через `/assistant/status`.

## Ошибки и повторы

```json
{
  "error": {
    "code": "CONFLICT",
    "message": "Конфликт данных.",
    "request_id": "77777777-7777-4777-8777-777777777777",
    "details": {
      "field": "revision"
    }
  }
}
```

| HTTP | Что проверить |
|---|---|
| 401 | Токен отсутствует, истёк или не принят |
| 403 | У роли нет нужного права |
| 404 | Объект не найден или недоступен |
| 409 | Связи, текущее состояние, уникальность или ревизия конфликтуют с операцией |
| 422 | Поля запроса; подробности могут быть в `details.field_errors` |
| 429 | Лимит запросов или занятость ИИ; задержка может быть в `details.retry_after_seconds` |
| 503 | Временная недоступность зависимости или отключённая возможность |
| 504 | Истекло время ожидания |

Для конкретной обработки используйте `error.code`. Один HTTP-код может соответствовать разным причинам. Полный список кодов есть на вкладке Ошибки и ограничения.

Общего idempotency key для всех POST нет. После разрыва соединения запись могла сохраниться. Не повторяйте создание, отправку уведомления или запуск отчёта автоматически. Сначала проверьте результат; повтор должен учитывать логику конкретного метода.

Ограничения стенда доступны в каталоге API. Дополнительные ограничения полей и файлов смотрите в карточке метода. Не записывайте в журналы Authorization, client secret, пароли и полные тела с персональными данными.

## Машиночитаемые точки входа

| Запрос | Результат |
|---|---|
| `GET /api/v1/auth/me` | Текущий аккаунт и права |
| `GET /api/v1/service-api` | Каталог методов, доступ роли, параметры авторизации, ограничения и коды ошибок |
| `GET /api/v1/openapi.json` | Полная схема OpenAPI через стандартный API-прокси |

Все три запроса требуют Bearer. Прямой backend дополнительно публикует `/docs` со Swagger UI, `/redoc` и `/openapi.json`. На сайте путь `/docs` занят справочным центром, поэтому для схемы используйте `/api/v1/openapi.json`, а не относительный `/openapi.json`.
