# Администрирование

## Роли и область доступа

Рабочие роли realm `rtk`: `admin`, `manager` и `user`. Роль руководителя не даёт прав изменять каталоги, запускать импорт и редактировать шаблоны Workflow. Для `user` и `manager` нужны назначения вузов в `university_ids`. Пустые назначения означают пустую область доступа; только администратор имеет доступ ко всем вузам.

В разделе Пользователи и права администратор управляет учётными записями, ролями, блокировкой и назначениями. Руководитель работает с назначениями в своей доступной области через Пользователи и вузы. Граф связей помогает проверить привязки. После изменения назначений пользователь должен обновить токен, например повторным входом.

Личные заметки и диалоги помощника не становятся общими для администратора: чтение и изменение проверяют владельца.

## Keycloak

В локальном Compose консоль доступна на http://localhost:8081. Учётные данные bootstrap-администратора задаются `KEYCLOAK_ADMIN` и `KEYCLOAK_ADMIN_PASSWORD`; это отдельная учётная запись от демо-пользователя `admin` в realm `rtk`.

При первом запуске импортируется `keycloak/realm-export.json`. Повторный запуск не обновляет существующий realm. Клиент `rtk-frontend` публичный и использует PKCE S256. Токен должен содержать audience `rtk-api`; backend проверяет подпись, срок действия, issuer и audience.

Для смены адреса CRM или Swagger настройте Redirect URIs и Web Origins, затем пересоберите frontend с актуальными публичными параметрами. [Установка](INSTALL.md), [Swagger](SWAGGER_AUTH_GUIDE.md).

## Каталоги, импорт и шаблоны

Администратор управляет вузами, направлениями, программами, продуктами, вендорами, ответственными, договорами и лицензиями. Связи программ, продуктов и ответственных с доступным вузом регулируются отдельно от прав на изменение самого справочника.

Импорт начинается с загрузки файла и предпросмотра листа, затем запускается обработка. Staging хранится в томе `import-staging`, задания выполняет worker. При ошибках используйте сведения о строке и колонке, исправьте исходный файл и повторите проверку.

Шаблоны Workflow редактирует администратор. Этапы могут содержать типовые задачи, которые копируются в новые процессы. Общий seed не создаёт шаблоны. Стандартный маршрут на 14 этапов устанавливается явно через `scripts/create_workflow_template.py`.

В процессе возможны переходы вперёд и разрешённый возврат с причиной. История изменений сохраняется. Не подменяйте бизнес-операции прямыми изменениями таблиц.

## Уведомления и дополнительные функции

Уведомления внутри CRM и письма являются разными каналами. Почтовый канал требует SMTP и включения `EMAIL_NOTIFICATIONS_ENABLED`. Обработку выполняет worker. Изменения Workflow могут сохраняться даже при ошибке дополнительного уведомления: проверяйте логи доставки отдельно.

Помощник включается отдельным Compose-файлом; обычный запуск оставляет его выключенным. Для модели требуются Ollama и подготовка документации. Готовые ответы не используют модель, но сохраняются в базе диалогов. [Инструкция](ASSISTANT.md).

Базовое хранилище файлов локальное. Для S3/MinIO и реальных внешних интеграций нужны дополнительные настройки и согласованные подключения; одного изменения произвольного значения в `.env` недостаточно.

## Эксплуатация

```bash
docker compose ps
docker compose logs --tail 100 backend worker frontend keycloak
docker compose exec backend python scripts/migrate.py status
docker compose exec backend python scripts/migrate.py verify
```

Храните резервные копии обеих баз и файловых томов, проверяйте восстановление отдельно. Не используйте удаление томов для обычного обновления. Порядок запуска и резервирования описан в [INSTALL.md](INSTALL.md). Результаты аудита исходников и известные проблемы тестов: [PROJECT_AUDIT_2026-10-20.md](PROJECT_AUDIT_2026-10-20.md).
