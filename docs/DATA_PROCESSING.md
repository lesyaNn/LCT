# Обработка данных

## Миграции

Схема приложения определяется SQL-файлами в `backend/migrations`. При старте backend выполняется попытка принятия старой Alembic-базы через `baseline`, затем `up` и `verify`. Новая база проходит обычные SQL-миграции. Keycloak использует отдельную базу и собственное управление схемой.

```bash
docker compose exec backend python scripts/migrate.py status
docker compose exec backend python scripts/migrate.py verify
```

На дату аудита доступна 51 миграция, последняя `000051_notes_onboarding`. Команда `verify` проверяет журнал применённых версий и наличие ожидаемых таблиц. Она не сравнивает каждое поле, индекс и ограничение с эталонной схемой.

## Демо-данные

Канонический запуск: `python -m app.scripts.seed_demo` при `SEED_DEMO_DATA=true`. Повторный запуск ищет существующие записи по естественным ключам и не создаёт их заново. Относительные даты устанавливаются при первоначальном создании.

Текущий seed создаёт каталоги, пять вузов, связи, договоры, лицензии и встречи. Шаблоны, экземпляры и переходы Workflow не создаются. Стандартный шаблон на 14 этапов устанавливается отдельно через `scripts/create_workflow_template.py`. Назначения демо-пользователям выполняет `app.scripts.provision_demo_scope`. [Состав и команды](DEMO_SEED.md).

## API и доступ

Входные данные проверяются Pydantic на backend и Zod в соответствующих формах frontend. Ошибки используют envelope `error` с полями `code`, `message`, `request_id` и `details`.

Проверка JWT включает issuer, audience, подпись и срок действия. Затем проверяются действие и область доступа к вузам. Личные заметки и диалоги дополнительно ограничены владельцем. Политики интерфейса не заменяют эти проверки.

Большинство списков используют `page` и `page_size`; заметки используют `offset` и `limit`. Аналитика и отчёты принимают `UnifiedFilter`, включая даты, вузы, направления, программы, продукты, ответственных и статусы Workflow. Поля и допустимые значения нужно брать из текущего OpenAPI, а не переносить между разными методами без проверки.

Health Score запрашивается через `/api/v1/universities/{university_id}/health-score`. В текущем подключённом API нет ранее описанного отдельного batch-метода на 50 вузов.

## Импорт Excel

Импорт и вложения Workflow имеют разные контракты.

1. `POST /api/v1/import/upload` принимает Excel `.xlsx` или `.xls` и сохраняет файл в staging.
2. `POST /api/v1/import/sheets/preview` показывает заголовки и строки выбранного листа без записи импортируемых сущностей.
3. `POST /api/v1/import/execute` создаёт задание. Исполнение выполняет worker.
4. Журнал, статус и файл ошибок доступны через `/api/v1/import/jobs`.

Размер Excel-файла ограничен 10 МиБ константой `MAX_FILE_BYTES` модуля импорта. Поддержка `.xls` требует установленного `xlrd`, который указан в зависимостях backend. Набор импортируемых сущностей и правила листов определяются модулем импорта; произвольные PDF или архивы не являются Excel-импортом.

Файлы staging находятся в `IMPORT_STAGING_DIR` и общем томе `import-staging`. Права на просмотр журнала и выполнение импорта различаются. Управление импортом в текущей модели относится к администратору.

## Отчёты и задания

Долгие отчёты XLS, XLSX, PDF и JSON, а также импорт исполняются через очередь в PostgreSQL. `POST /api/v1/reports` возвращает 202 и идентификатор задания.

Worker получает задание атомарным claim через `SELECT ... FOR UPDATE SKIP LOCKED`. После выполнения записываются состояние и результат. При исчерпании попыток задание переходит в `failed`; текущий предел составляет три попытки.

Статус отчёта: `GET /api/v1/reports/{job_id}`. Скачивание: `GET /api/v1/reports/{job_id}/download`. Файл хранится в `reports-storage`; одного работающего API без worker недостаточно.

## Внешние данные

По умолчанию `EXTERNAL_ADAPTER_MODE=disabled`. Внешние источники не подключены, соответствующие операции могут возвращать 503 с `EXTERNAL_SOURCE_UNAVAILABLE`. Ошибка реального источника не заменяется демонстрационными данными.

Методы приёма: `/api/v1/integrations/lms/ingest` и `/api/v1/integrations/website/ingest`. Применяются ограничения размера, проверка источника и дедупликация. [Контракты](EXTERNAL_EDUCATION_CONTRACTS.md). Файл импорта заявок не требует действующего live-подключения к сайту.

## Аудит и уведомления

Бизнес-изменения используют `AuditService` и журнал аудита; публичных методов редактирования и удаления аудита нет. Некоторые события передаются через outbox. Seed не создаёт пользовательскую историю действий и не выполняет переходы Workflow.

Уведомления внутри CRM и почтовая доставка являются отдельными каналами. Worker обрабатывает очереди доставки и напоминания. Сохранённая операция или внутреннее уведомление не подтверждают отправку email. SMTP должен быть настроен отдельно.

LOGIN и LOGOUT не входят в журнал бизнес-аудита. Журнал не является криптографически неизменяемым хранилищем. [Границы механизмов безопасности](SECURITY_ALIGNMENT.md).

## Файлы, кэш и помощник

Вложения Workflow проходят отдельные проверки размера, расширения и допустимого пути. Метаданные находятся в PostgreSQL, содержимое по умолчанию в локальном томе. S3/MinIO требует настройки адаптера и передачи параметров контейнеру.

Redis 7 используется как кэш, а постоянные бизнес-данные и задания хранятся в PostgreSQL.

Помощник читает только разрешённые опубликованные статьи из `frontend/public/docs`, а не весь репозиторий или данные вузов. История диалогов находится в PostgreSQL. Веса и индекс при Docker-запуске сохраняются в отдельных томах. Ответ может быть готовым FAQ либо результатом локальной генерации. [Подробности](ASSISTANT.md).
