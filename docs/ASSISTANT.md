# Помощник по документации

Помощник доступен через виджет CRM и JSON API FastAPI. Он отвечает по опубликованным инструкциям, возвращает источники и хранит личные диалоги в PostgreSQL. Виджет находится в `frontend/widgets/assistant`.

## Как устроен ответ

Сервер находит подходящие фрагменты инструкций и передаёт их локальной модели Qwen3 1.7B через Ollama. Поиск использует BM25 и Qwen3 Embedding 0.6B. В запрос попадают до трёх фрагментов и до трёх предыдущих вопросов с ответами. История сокращается с учётом места, занятого текущим вопросом и документами.

Уверенно распознанный вопрос из FAQ получает готовый опубликованный ответ без обращения к модели. Это быстрый путь, а не выдуманный ответ и не общий кэш пользовательских диалогов. Сложные формулировки и неоднозначные совпадения обрабатываются моделью.

Короткие приветствия, включая Привет, как дела?, получают отдельный серверный ответ без модели, embedding и предыдущей темы разговора. Ответ сохраняется в историю с `model=null`, `basis=insufficient` и пустыми источниками: это приветствие, не факт из документации. Вопрос с дополнительным содержанием, например Привет, как скачать отчёт?, не заменяется приветствием.

При каждом открытии окна виджет показывает приветственный текст, а не прокручивает сразу к концу старой переписки. Кнопка Новый диалог начинает разговор без прежнего контекста. Сохранённая история не удаляется; при перезагрузке восстанавливается последний сохранённый диалог.

Явные команды выполнить действие и запросы системных инструкций или секретов получают серверный отказ без вызова модели. Это дополнительная проверка, не универсальный детектор инъекций. Основные ограничения сохраняются всегда: модель видит только разрешённые инструкции, не получает бизнес-данные и не имеет инструментов изменения CRM.

В базу знаний включены 19 опубликованных статей из `frontend/public/docs`. Перечень задаётся в `backend/app/modules/assistant/knowledge.py`. Старые аудиты, исходники, `.env` и загруженные пользователями файлы не индексируются. Статьи про управление каталогами, импорт, пользователей и шаблоны доступны только администратору. Статья о роли руководителя доступна руководителю и администратору. Общие инструкции и FAQ доступны всем трём ролям. Новые статьи о заметках, карте или API не попадают в индекс автоматически, если их нет в этом перечне.

Модель не получает JWT, email, имя пользователя или данные вузов из CRM. Введённые пользователем вопрос и история передаются модели: поэтому в чат не следует отправлять пароли и лишние персональные данные. Модель не выполняет действия в CRM. Допустимые ID источников ограничены схемой генерации и повторно проверяются сервером; ссылки собираются из опубликованных статей. При недостатке сведений возвращается `basis=insufficient`, косвенный вывод получает `basis=inference` и явную пометку. Это снижает ошибки, но не гарантирует безошибочность любой генерации.

## Запуск с Docker

Обычный `docker-compose.yml` оставляет помощника выключенным. Дополнительный файл включает backend настройки, подключает инструкции только для чтения и запускает Ollama в приватной сети без публикации порта.

Из корня проекта, при установленном и запущенном Docker Compose:

Используется существующий `.env` проекта. Скрипт не меняет пароли и не отключает авторизацию. Для нового стенда сначала выполните базовую настройку из [INSTALL.md](INSTALL.md).

```bash
python backend/scripts/start_assistant.py
```

Команда проверяет Compose, собирает и запускает backend с зависимостями, скачивает отсутствующие веса, создаёт индекс, прогревает модель настоящей генерацией JSON и проверяет модель, документацию и таблицы диалогов. Повторный запуск использует сохранённые модели и актуальный индекс. Около 2 ГБ требуется только на веса; образы Docker скачиваются отдельно.

CRM запускается до загрузки весов. Ошибка подготовки помощника завершает команду с ненулевым кодом, но не останавливает CRM. Обычный запуск без overlay оставляет помощника выключенным.

Эквивалентные отдельные шаги:

```bash
docker compose -f docker-compose.yml -f docker-compose.assistant.yml --profile assistant up -d --build backend
docker compose -f docker-compose.yml -f docker-compose.assistant.yml --profile assistant run --rm --no-deps assistant-init
docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec -T backend python -m scripts.assistant check
```

Диагностика:

```bash
docker compose -f docker-compose.yml -f docker-compose.assistant.yml logs --tail 100 ollama
docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec -T backend python -m scripts.assistant check
```

Модели скачивает только явная команда подготовки, не HTTP-запрос к чату. Индекс хранится в томе `assistant-index`, веса в `assistant-models`. Тома сохраняются при пересоздании контейнеров. Индекс принадлежит пользователю `appuser`, инструкции подключены только для чтения. Порт Ollama наружу не публикуется.

По умолчанию используется CPU-профиль Qwen3 1.7B: один запрос генерации одновременно, контекст 4096 токенов, максимум 256 новых токенов, рассуждения выключены. Ollama держит в памяти одну модель; это экономит RAM, но переключение между embedding и chat добавляет задержку. Быстрые FAQ не загружают модели.

Для более мощного стенда доступен `python backend/scripts/start_assistant.py --model qwen3:4b`. Вариант 4B не проверялся на этом ноутбуке. Qwen3 0.6B проверена и исключена из подготовленных профилей: не прошла приёмочные сценарии. Для всего CRM-стенда с Keycloak и PostgreSQL нужен запас ресурсов сверх размера весов. Новый ответ на CPU может занимать десятки секунд; FAQ обрабатывается быстрее. Фактические замеры приведены в [отчёте проверки](ASSISTANT_VALIDATION.md).

## Локальная разработка

Запустите Ollama и скачайте те же модели. Для FastAPI задайте:

```dotenv
ASSISTANT_ENABLED=true
ASSISTANT_OLLAMA_URL=http://localhost:11434
ASSISTANT_MODEL=qwen3:1.7b
ASSISTANT_EMBEDDING_MODEL=qwen3-embedding:0.6b
```

Примените миграции обычным способом. Миграция помощника: `000044_assistant_conversations`. Она создаёт только таблицы диалогов и ответов. Из каталога `backend`:

```bash
python -m scripts.assistant bootstrap
python -m scripts.assistant check
```

Путь к статьям по умолчанию вычисляется относительно репозитория. В базовом Docker Compose каталог инструкций подключён к backend через `ASSISTANT_DOCS_ROOT`; при отдельной поставке образа backend его также нужно подключить явно.

## Контракт для frontend

Быстрые кнопки, десять согласованных ответов и новый каталог вопросов описаны в [ASSISTANT_QUICK_REPLIES.md](ASSISTANT_QUICK_REPLIES.md). Они работают без вызова модели и сохраняются в обычную историю.

Все методы требуют обычный Bearer JWT Keycloak и право `assistant.use`. Оно входит в роли `user`, `manager`, `admin`. Base URL: `/api/v1/assistant`. Все ответы, включая ошибки, имеют `Cache-Control: no-store`.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/status` | Включён ли помощник, доступна ли модель, режим поиска, версия базы знаний |
| GET | `/quick-replies` | Каталог десяти готовых вопросов, не требующий загрузки модели |
| POST | `/chat` | Новая пара вопрос/ответ или продолжение диалога |
| GET | `/conversations?page=1&page_size=20` | Свои диалоги, новые в начале |
| GET | `/conversations/{id}?page=1&page_size=20` | Свои вопросы и ответы, в хронологическом порядке |
| DELETE | `/conversations/{id}` | Удаление диалога и всех его сообщений, ответ 204 |

### Новый вопрос

```http
POST /api/v1/assistant/chat
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "message": "Как вернуть Workflow на предыдущий этап?",
  "page": "workflow"
}
```

Пример ответа. Идентификаторы и версия приведены для иллюстрации:

```json
{
  "conversation_id": "59e27925-3362-46ac-9bfe-f59dad83f6d3",
  "turn_id": "57b51d4f-2fe4-498e-bd43-28a006097672",
  "revision": 1,
  "answer": "Откройте Workflow, нажмите «Вернуть на предыдущий этап» и укажите причину. Действие доступно, если возврат разрешён.",
  "basis": "documentation",
  "sources": [
    {
      "id": "6e59d6875798299c",
      "title": "Workflow",
      "url": "/docs?article=user-guide%2Fworkflow",
      "excerpt": "Если возврат разрешён, используйте «Вернуть на предыдущий этап» и укажите причину."
    }
  ],
  "knowledge_version": "ade0f4ed58fda1fa9180060279d593993874b22511373dfb63dc4fedf2669a91",
  "retrieval_mode": "hybrid",
  "model": "qwen3:1.7b",
  "created_at": "2026-10-16T12:00:00Z"
}
```

`basis` принимает `documentation`, `inference` или `insufficient`. Числовой процент уверенности намеренно не возвращается. `sources` содержит только использованные источники; при недостатке сведений массив пуст. `retrieval_mode` показывает фактический поиск. `model=null` означает, что генерация не использовалась: это готовый FAQ или ответ о недостатке сведений. Текст и отрывки нужно отображать как текст либо через безопасный Markdown renderer.

`page` необязателен. Допустимые значения: `dashboard`, `universities`, `university`, `workflows`, `workflow`, `reports`, `audit`, `catalogs`, `import`, `users`, `workflow_templates`, `docs`. Сервер использует его как подсказку для поиска, не как подтверждение прав.

### Продолжение

```json
{
  "conversation_id": "59e27925-3362-46ac-9bfe-f59dad83f6d3",
  "expected_revision": 1,
  "message": "А нужно ли указывать причину?",
  "page": "workflow"
}
```

Клиент передаёт только новое сообщение. Историю и системную инструкцию формирует backend. `expected_revision` необязателен, но рекомендуется. Виджет перед каждой отправкой перечитывает историю и обновляет версию, в том числе после ошибки предыдущего запроса. Если POST явно отклонён с 409 и `details.field=revision`, виджет синхронизирует историю и повторяет запрос один раз. Повторный конфликт требует ручного действия. Сетевые ошибки и ошибки модели автоматически не повторяются: результат такого запроса может быть неизвестен. Повтор после уже сохранённого успешного ответа создаёт новый ход.

Конфликт с `details.reason=turn_limit` не является устаревшей версией. Виджет предлагает начать Новый диалог и не повторяет такой запрос автоматически.

### История

Список диалогов возвращает `items`, `total`, `page`, `page_size`. Элемент содержит `id`, `title`, `revision`, `created_at`, `updated_at`. История одного диалога возвращает те же поля пагинации, объект `conversation` и пары вопрос/ответ в `items`. У пары есть все поля ответа `/chat` и дополнительное `question`. Максимальный размер страницы равен 50.

Чужой диалог возвращает 404, в том числе для администратора. После смены эффективной роли старые диалоги не показываются в новой роли: привилегированный контекст не переносится автоматически. Для следующего вопроса нужно создать новый диалог.

### Готовность и ошибки

`GET /status` возвращает `enabled`, `ready`, `reason`, `model`, `retrieval_mode`, `document_count`, `knowledge_version`. Значение `reason`: `disabled`, `knowledge_missing`, `model_unavailable`, `storage_unavailable` или `ready`. Проверяются доступная модель, инструкции и обе таблицы диалогов без чтения чужого содержимого. Отсутствие embedding-модели отражается как текстовый поиск. Готовность не обещает скорость и качество любого ответа; настоящая генерация проверяется при подготовке.

Ошибки используют общий envelope CRM:

```json
{
  "error": {
    "code": "ASSISTANT_TIMEOUT",
    "message": "Помощник не успел ответить. Попробуйте позже.",
    "request_id": "501b09a4-e248-4531-b3d3-67a33f449794",
    "details": {}
  }
}
```

| HTTP | Код | Что показать пользователю |
|---|---|---|
| 401 | `AUTH_REQUIRED`, `TOKEN_EXPIRED`, `TOKEN_INVALID` | Требуется вход |
| 403 | `FORBIDDEN` | Нет права на помощника |
| 404 | `NOT_FOUND` | Диалог отсутствует, истёк или недоступен |
| 409 | `CONFLICT` | История изменилась или достигнут лимит ходов |
| 422 | `VALIDATION_ERROR` | Исправить поля запроса |
| 429 | `RATE_LIMITED`, `ASSISTANT_BUSY` | Повторить через `details.retry_after_seconds` секунд |
| 503 | `ASSISTANT_DISABLED` | Помощник выключен |
| 503 | `ASSISTANT_UNAVAILABLE` | Ollama или модель недоступны |
| 503 | `ASSISTANT_KNOWLEDGE_UNAVAILABLE` | Нет доступных инструкций |
| 503 | `ASSISTANT_INVALID_RESPONSE` | Модель не сформировала проверяемый ответ |
| 503 | `ASSISTANT_STORAGE_UNAVAILABLE` | История временно недоступна |
| 504 | `ASSISTANT_TIMEOUT` | Генерация превысила время ожидания |

## Обновление знаний и хранение

Документы перечитываются после изменения файлов. Версия базы знаний вычисляется из содержимого. Старые embeddings при изменении документов или модели не используются; текстовый поиск продолжает работать. Для восстановления поиска по смыслу повторите `python -m scripts.assistant index`. Ошибка embedding модели также переключает конкретный запрос на текстовый поиск и отражается в `retrieval_mode`.

Хранятся только завершённые пары вопрос/ответ. Во время обращения к Ollama транзакция PostgreSQL закрыта. Обновление ревизии диалога и запись пары выполняются атомарно. На пользователя действует лимит 10 вопросов в минуту; ключ привязан к Keycloak sub, смена токена его не сбрасывает. По умолчанию процесс обслуживает один запрос генерации одновременно. Эти пределы настраиваются и действуют отдельно в каждой реплике backend.

По умолчанию диалог допускает 100 ходов. История скрывается через 30 дней после последнего ответа. Физическое удаление старых диалогов выполняет оператор или планировщик площадки:

```bash
python -m scripts.assistant purge
python -m scripts.assistant purge --execute
```

Первая команда только показывает количество, вторая удаляет истёкшие диалоги вместе с сообщениями. Для Docker добавьте префикс `docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec backend`. Вопросы и ответы могут содержать введённые пользователем сведения, поэтому в интерфейсе желательно попросить не отправлять пароли и лишние персональные данные. Они не дублируются в прикладные логи или аудит.

## Проверки

```bash
cd backend
python -m pytest tests/test_assistant.py tests/test_assistant_pg.py tests/test_assistant_deploy.py -q
```

Быстрые тесты поиска и ошибок используют HTTP mock Ollama. PostgreSQL-тесты проверяют реальную SQL-миграцию, хранение JSON, доступ, параллельную запись и каскадное удаление. Для них нужна отдельная БД с `test` в названии через `TEST_DATABASE_URL`; fixture пересоздаёт её схему. В этих тестах не скачиваются веса.

Приёмочная проверка с настоящей моделью и базой:

```bash
# TEST_DATABASE_URL должна указывать на отдельную мигрированную тестовую базу.
# ASSISTANT_INDEX_PATH должен указывать на построенный индекс.
python -m scripts.assistant_eval --output var/assistant-live/acceptance.json
```

Проверка отправляет восемь синтетических вопросов через настоящий API-маршрут и middleware, затем проверяет продолжение, историю, чужие роли, конфликт ревизии и удаление. JWT подписываются временным тестовым ключом, штатная проверка RS256/issuer/audience/exp не отключается. Это не проверка живого Keycloak или frontend-виджета. SQL и генерация Ollama настоящие, без моков. Созданные тестовые диалоги удаляются; схема и остальные данные не сбрасываются. JSON-отчёт содержит только синтетические вопросы и ответы, без JWT и адреса базы.

Документация провайдера: [Ollama chat](https://docs.ollama.com/api/chat), [Ollama embeddings](https://docs.ollama.com/api/embed), [Qwen3 Embedding 0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B).
