# Помощник по документации

Backend помощника работает через JSON API FastAPI. Он отвечает по опубликованным инструкциям CRM, возвращает источники и хранит личные диалоги в PostgreSQL. Frontend виджет в эту ветку не входит.

## Как устроен ответ

Сервер находит подходящие фрагменты инструкций и передаёт их локальной модели Qwen3 4B через Ollama. Поиск использует BM25 с нормализацией русских слов. После построения векторного индекса к нему добавляется поиск по смыслу через Qwen3 Embedding 0.6B. Результаты объединяются, в запрос модели попадают до четырёх фрагментов и три предыдущих вопроса с ответами.

В базу знаний включены 19 опубликованных статей из `frontend/public/docs`. Файлы читаются сервером, без изменений frontend. Перечень задаётся в `backend/app/modules/assistant/knowledge.py`. Старые аудиты, исходники, `.env` и загруженные пользователями файлы не индексируются. Статьи про импорт и каталоги доступны менеджеру и администратору. Статьи про управление пользователями и шаблонами доступны только администратору. Общие инструкции и FAQ доступны всем трём ролям.

Модель не получает JWT, email, имя пользователя или данные вузов. Она не выполняет действия в CRM. Источники и ссылки собирает сервер из найденных статей; произвольная ссылка модели источником не становится. Если оснований нет, возвращается `basis=insufficient`. Вывод по косвенным сведениям получает `basis=inference` и явную пометку в тексте. Эти меры снижают ошибки, но качество ответов всё равно нужно оценить на вопросах пользователей.

## Запуск с Docker

Обычный `docker-compose.yml` оставляет помощника выключенным. Дополнительный файл включает backend настройки, подключает инструкции только для чтения и запускает Ollama в приватной сети без публикации порта.

Из корня проекта:

```bash
docker compose -f docker-compose.yml -f docker-compose.assistant.yml --profile assistant up -d --build
```

Скачать модель для ответов:

```bash
docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec ollama ollama pull qwen3:4b
```

После этого уже работает текстовый поиск и генерация ответов. Для поиска по смыслу:

```bash
docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec ollama ollama pull qwen3-embedding:0.6b
docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec backend python -m scripts.assistant index
```

Модели скачиваются только этими командами, не при HTTP запросе к чату. Векторный индекс хранится в томе `assistant-index`, веса моделей в `assistant-models`. Оба тома сохраняются при пересоздании контейнеров. Образ backend готовит каталог индекса с правами пользователя `appuser`.

Сборка Qwen3 4B в Ollama занимает около 2,5 ГБ на диске; это не полное потребление оперативной памяти. Для всего стенда начальный ориентир составляет 16 ГБ RAM. Скорость зависит от процессора, GPU, размера контекста и числа пользователей. Compose настроен на CPU; для NVIDIA можно добавить `gpus: all` сервису Ollama в собственном override при установленном NVIDIA Container Toolkit. Режим рассуждений выключен через `think=false`, контекст ограничен 8192 токенами. При холодном старте на CPU может потребоваться `ASSISTANT_TIMEOUT_SECONDS=180` и пересоздание backend.

## Локальная разработка

Запустите Ollama и скачайте те же модели. Для FastAPI задайте:

```dotenv
ASSISTANT_ENABLED=true
ASSISTANT_OLLAMA_URL=http://localhost:11434
ASSISTANT_MODEL=qwen3:4b
ASSISTANT_EMBEDDING_MODEL=qwen3-embedding:0.6b
```

Примените миграции обычным способом. Миграция помощника: `000044_assistant_conversations`. Она создаёт только таблицы диалогов и ответов. Из каталога `backend`:

```bash
python -m scripts.assistant inspect
python -m scripts.assistant index
```

Путь к статьям по умолчанию вычисляется относительно репозитория. В базовом Docker Compose каталог инструкций подключён к backend через `ASSISTANT_DOCS_ROOT`; при отдельной поставке образа backend его также нужно подключить явно.

## Контракт для frontend

Все методы требуют обычный Bearer JWT Keycloak и право `assistant.use`. Оно входит в роли `user`, `manager`, `admin`. Base URL: `/api/v1/assistant`. Все ответы, включая ошибки, имеют `Cache-Control: no-store`.

| Метод | Путь | Результат |
|---|---|---|
| GET | `/status` | Включён ли помощник, доступна ли модель, режим поиска, версия базы знаний |
| POST | `/chat` | Новая пара вопрос/ответ или продолжение диалога |
| GET | `/conversations?page=1&page_size=20` | Свои диалоги, новые в начале |
| GET | `/conversations/{id}?page=1&page_size=20` | Свои вопросы и ответы, в хронологическом порядке |
| DELETE | `/conversations/{id}` | Удаление диалога и всех его сообщений, ответ 204 |

### Новый вопрос

```http
POST /api/v1/assistant/chat
Authorization: Bearer <access_token>
Content-Type: application/json
```

```json
{
  "message": "Как вернуть Workflow на предыдущий этап?",
  "page": "workflow"
}
```

Пример ответа. Идентификаторы и версия приведены для иллюстрации:

```json
{
  "conversation_id": "59e27925-3362-46ac-9bfe-f59dad83f6d3",
  "turn_id": "57b51d4f-2fe4-498e-bd43-28a006097672",
  "revision": 1,
  "answer": "Откройте Workflow, нажмите «Вернуть на предыдущий этап» и укажите причину. Действие доступно, если возврат разрешён.",
  "basis": "documentation",
  "sources": [
    {
      "id": "6e59d6875798299c",
      "title": "Workflow",
      "url": "/docs?article=user-guide%2Fworkflow",
      "excerpt": "Если возврат разрешён, используйте «Вернуть на предыдущий этап» и укажите причину."
    }
  ],
  "knowledge_version": "ade0f4ed58fda1fa9180060279d593993874b22511373dfb63dc4fedf2669a91",
  "retrieval_mode": "hybrid",
  "model": "qwen3:4b",
  "created_at": "2026-10-16T12:00:00Z"
}
```

`basis` принимает `documentation`, `inference` или `insufficient`. Числовой процент уверенности намеренно не возвращается. `sources` содержит только использованные источники; при недостатке сведений массив пуст. `retrieval_mode` показывает фактически использованный поиск. `model=null`, если ответ о недостатке сведений получен без обращения к модели. Текст ответа и отрывки нужно отображать как текст либо через безопасный Markdown renderer.

`page` необязателен. Допустимые значения: `dashboard`, `universities`, `university`, `workflows`, `workflow`, `reports`, `audit`, `catalogs`, `import`, `users`, `workflow_templates`, `docs`. Сервер использует его как подсказку для поиска, не как подтверждение прав.

### Продолжение

```json
{
  "conversation_id": "59e27925-3362-46ac-9bfe-f59dad83f6d3",
  "expected_revision": 1,
  "message": "А нужно ли указывать причину?",
  "page": "workflow"
}
```

Клиент передаёт только новое сообщение. Историю и системную инструкцию формирует backend. `expected_revision` необязателен, но рекомендуется. При параллельных сообщениях один запрос может получить 409; нужно перечитать историю и предложить повторную отправку. Автоматического повтора POST нет: повтор после уже полученного успешного ответа создаёт новый ход.

### История

Список диалогов возвращает `items`, `total`, `page`, `page_size`. Элемент содержит `id`, `title`, `revision`, `created_at`, `updated_at`. История одного диалога возвращает те же поля пагинации, объект `conversation` и пары вопрос/ответ в `items`. У пары есть все поля ответа `/chat` и дополнительное `question`. Максимальный размер страницы равен 50.

Чужой диалог возвращает 404, в том числе для администратора. После смены эффективной роли старые диалоги не показываются в новой роли: привилегированный контекст не переносится автоматически. Для следующего вопроса нужно создать новый диалог.

### Готовность и ошибки

`GET /status` возвращает `enabled`, `ready`, `reason`, `model`, `retrieval_mode`, `document_count`, `knowledge_version`. Значение `reason`: `disabled`, `knowledge_missing`, `model_unavailable` или `ready`. Это проверка доступности модели и инструкций, а не измерение скорости или качества генерации.

Ошибки используют общий envelope CRM:

```json
{
  "error": {
    "code": "ASSISTANT_TIMEOUT",
    "message": "Помощник не успел ответить. Попробуйте позже.",
    "request_id": "501b09a4-e248-4531-b3d3-67a33f449794",
    "details": {}
  }
}
```

| HTTP | Код | Что показать пользователю |
|---|---|---|
| 401 | `AUTH_REQUIRED`, `TOKEN_EXPIRED`, `TOKEN_INVALID` | Требуется вход |
| 403 | `FORBIDDEN` | Нет права на помощника |
| 404 | `NOT_FOUND` | Диалог отсутствует, истёк или недоступен |
| 409 | `CONFLICT` | История изменилась или достигнут лимит ходов |
| 422 | `VALIDATION_ERROR` | Исправить поля запроса |
| 429 | `RATE_LIMITED`, `ASSISTANT_BUSY` | Повторить через `details.retry_after_seconds` секунд |
| 503 | `ASSISTANT_DISABLED` | Помощник выключен |
| 503 | `ASSISTANT_UNAVAILABLE` | Ollama или модель недоступны |
| 503 | `ASSISTANT_KNOWLEDGE_UNAVAILABLE` | Нет доступных инструкций |
| 503 | `ASSISTANT_INVALID_RESPONSE` | Модель не сформировала проверяемый ответ |
| 503 | `ASSISTANT_STORAGE_UNAVAILABLE` | История временно недоступна |
| 504 | `ASSISTANT_TIMEOUT` | Генерация превысила время ожидания |

## Обновление знаний и хранение

Документы перечитываются после изменения файлов. Версия базы знаний вычисляется из содержимого. Старые embeddings при изменении документов или модели не используются; текстовый поиск продолжает работать. Для восстановления поиска по смыслу повторите `python -m scripts.assistant index`. Ошибка embedding модели также переключает конкретный запрос на текстовый поиск и отражается в `retrieval_mode`.

Хранятся только завершённые пары вопрос/ответ. Во время обращения к Ollama транзакция PostgreSQL закрыта. Обновление ревизии диалога и запись пары выполняются атомарно. На пользователя действует лимит 10 вопросов в минуту; ключ привязан к Keycloak sub, смена токена его не сбрасывает. На процесс backend допускаются два одновременных запроса. Эти пределы настраиваются. Лимит активных запросов действует отдельно в каждой реплике backend.

По умолчанию диалог допускает 100 ходов. История скрывается через 30 дней после последнего ответа. Физическое удаление старых диалогов выполняет оператор или планировщик площадки:

```bash
python -m scripts.assistant purge
python -m scripts.assistant purge --execute
```

Первая команда только показывает количество, вторая удаляет истёкшие диалоги вместе с сообщениями. Для Docker добавьте префикс `docker compose -f docker-compose.yml -f docker-compose.assistant.yml exec backend`. Вопросы и ответы могут содержать введённые пользователем сведения, поэтому в интерфейсе желательно попросить не отправлять пароли и лишние персональные данные. Они не дублируются в прикладные логи или аудит.

## Проверки

```bash
cd backend
python -m pytest tests/test_assistant.py tests/test_assistant_pg.py -q
```

Тесты поиска и API используют HTTP mock Ollama. PostgreSQL тесты проверяют реальную SQL миграцию, хранение JSON, границы доступа, параллельную запись и каскадное удаление. Для них нужна отдельная БД с `test` в названии через `TEST_DATABASE_URL`; существующий fixture проекта пересоздаёт её схему. В тестах не скачиваются веса моделей. Скорость и содержательность ответов настоящей модели проверяются отдельно на целевой машине.

Документация провайдера: [Ollama chat](https://docs.ollama.com/api/chat), [Ollama embeddings](https://docs.ollama.com/api/embed), [Qwen3 Embedding 0.6B](https://huggingface.co/Qwen/Qwen3-Embedding-0.6B).
