# API сервиса

Ветка `codex/raisw-service-api`. Базовый коммит `809279b`. Ниже зафиксированы результаты локальной приёмки перед отправкой в репозиторий.

## Результат

Переиспользованы 154 действующие операции CRM. Добавлены два GET: `/api/v1/service-api` с каталогом методов и `/api/v1/openapi.json` со схемой. Теперь в каталоге 156 операций. Новых таблиц и второй реализации CRUD нет.

На сайте добавлена вкладка API по адресу `/api`. В ней находятся инструкция подключения, поиск и фильтры методов, права, поля, примеры запросов, ответы и скачивание OpenAPI. В справочном центре появилась та же инструкция в разделе API.

Каталог собирается из подключённых маршрутов. Права берутся из зависимостей авторизации, а не из текста описаний. `role_allowed` не отменяет проверки области доступа и состояния объекта. RBAC, проверки JWT и правила удаления не менялись.

Текст инструкции: `frontend/public/docs/api/integration.md`. Серверный код: `backend/app/modules/service_api`. Компонент страницы: `frontend/widgets/api-documentation`.

Учёта тендеров в проекте нет. Отдельный модуль тендеров не создавался.

OIDC-обмен в браузерных тестах имитируется; отдельно серверные тесты проверяют JWT с настоящей RSA-подписью, неверный audience и неизвестную роль. Изменяющих запросов к CRM страница не отправляет.

Проверены 16 примеров запросов в OpenAPI и 12 JSON-примеров инструкции по фактическим Pydantic-моделям.

## Состояние общего набора тестов

Прогон `backend/tests` с локальными PDF-шрифтами дал 627 passed, 502 skipped и два падения. Два теста с ошибками импорта проверялись отдельно. Все четыре проблемы воспроизводятся на исходном коде `809279b` из резервной копии:

1. `test_p5_audit_context_guard.py`: загрузка документа паспорта использует `get_db` вместо ожидаемого тестом `get_audit_db`.
2. `test_p5_mocks_coverage.py`: в старом mock Workflow отсутствует `started_at` у этапов.
3. `test_default_workflow_bootstrap.py`: импорт отсутствующего `DEFAULT_STAGES`.
4. `test_seed_demo.py`: импорт отсутствующего `DEMO_TEMPLATE_NAME`.

Они не исправлялись в рамках API. Пропущенные DB-тесты не считаются проверенными; отдельно выполненные три PostgreSQL-проверки указаны выше.

## Подключение на стенде

Нужно пересобрать frontend и backend. Миграций для этой задачи нет. После входа в CRM откройте `/api`.

Методы работают с существующим Keycloak Bearer JWT. Для автономной серверной интеграции администратору нужно отдельно создать сервисный OIDC client, назначить минимальную роль и настроить audience и область вузов. Готового сервисного клиента с общим секретом в репозиторий не добавлялось. Инструкция содержит порядок настройки и пример обмена `client_credentials`.
